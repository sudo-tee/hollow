# Mixed filesystem/exec contention: eight PTYs

Follow-up to the [shared scheduler experiment](2026-10-18-shared-pty.md).
**No production code, scheduling policy, admission limits or defaults change.**
This adds a bounded interference source to the headless benchmark and measures
the existing scheduler, not a new scheduler candidate or rollout qualification.

## Workload and interpretation

Three independent runs per combination: native Linux POSIX, dedicated agent,
shared agent; eight PTYs; noisy or one-stalled-consumer load; bulk off or mixed;
prompt or 10 MiB foreground output. This produces **72 measurements**, with 1,000
recorded prompt exchanges per prompt run after 32 checked warmups. Backend order
alternates. Every foreground exits cleanly and output bytes/checksums match.
Consuming background PTYs emit checked distinct bytes; the stalled background
is never consumed. Sources, buffering and finite-background limits remain as in
the preceding report. All dataset rows retain `qualification: false`.

Mixed bulk repeatedly issues one 16 KiB `FS_READ` and one 512 KiB non-PTY `EXEC`,
at most one pending request of each kind. The exec captures `head -c 524288
/dev/zero` output; it produces bounded completion bursts, not an unbounded live
exec stream. Exact lengths and all-zero contents are verified before reissuing.
One completion per enabled operation primes the connection before load; bulk
counters then reset and include subsequent foreground prompt warmups. Pending
work is cancelled at teardown rather than counted as a completed transfer.

Shared mode puts both requests on the PTY connection. Native/dedicated modes use
one additional agent connection, labeled `separate_agent`; these are different
contention/failure boundaries. All run on the same Linux client inside WSL2, not
native Windows or the legacy WSL bypass. Owner-loop work and CPU contention still
affect separate connections: native mixed prompt latency also increases markedly.
A smaller shared-minus-native delta under bulk is not proof of a better scheduler.

The owner reads foreground first, services bulk completions/submissions, then
reads at most 16 KiB from each consuming background per receive iteration.
Bulk validation/decoding therefore adds owner-thread work on every backend.
Every 16th prompt, including warmups, issues an alternating-width resize before
input; 65 resizes are issued per prompt run in both off/mixed cases. Issuance is
checked, not resize-acknowledgement latency. Output runs do not resize.
There are no focus hints or logical-session hierarchy.

## Results

Prompt values are medians of three per-run p99 values, not pooled samples.
Throughput values are medians of three independent 10 MiB transfers.

| Load | Bulk | Native p99, ms | Dedicated p99, ms | Shared p99, ms | Shared foreground, MiB/s | Shared aggregate PTY, MiB/s |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| Noisy | Off | 1.753 | 2.475 | 6.478 | 9.43 | 75.46 |
| Noisy | Mixed | 6.011 | 4.126 | 9.891 | 6.13 | 49.06 |
| Stalled | Off | 1.485 | 2.423 | 6.618 | 11.01 | 75.89 |
| Stalled | Mixed | 5.832 | 3.729 | 9.402 | 7.30 | 51.33 |

Shared mixed prompt p99 ranges are **9.12–9.90 ms noisy** and **8.95–10.72 ms
stalled**. Two of six mixed shared/native pairs exceed the local +5 ms check;
three of six bulk-off pairs also exceed it. This is not the plan's required
legacy WSL-bypass comparison. Keep every slow run: bulk-off stalled shared p99
reaches 9.24 ms, with a 31.92 ms maximum individual prompt sample.

All enabled bulk operations and all consuming PTYs made checked progress.
The shared stalled buffer stays **exactly 65,536 bytes** in all prompt/output
runs. The largest observed shared background delivery gap is **32.16 ms**
(mixed stalled), versus 26.56 ms for bulk-off stalled. This is a shorter,
eight-PTY experiment, not evidence that the earlier 16-PTY 80.31 ms tail is fixed.

During shared mixed output runs, median completed fs/exec payload rates are
4.33/26.60 MiB/s noisy and 4.45/27.75 MiB/s stalled. Median total checked PTY +
completed fs + completed exec payload rates are 80.05/83.53 MiB/s. These count
application bytes, not wire bytes; DATA/response framing and metadata are excluded.
`FS_READ` payloads travel as binary DATA, not base64 (the original wording here
incorrectly implied base64 expansion; measured byte counts are unchanged).
Reduced PTY bandwidth partly reflects bandwidth delivered to bulk, not simply
lost aggregate capacity. Raw per-stream counts and per-run values remain available.

The bounded 64-bucket log2-nanosecond RPC histograms are owner-observed request
completion timings, including decode/verification and owner scheduling. They do
not locate dispatch, control-queue or pipe head-of-line stalls. During shared
mixed output runs the worst observed fs/exec completion latencies are
16.37/33.83 ms. These are maxima, not exact histogram percentiles or server timings.

**Decision: keep current defaults and reject shared-pane rollout.** Next useful
step is internal dispatch/control/output-queue timing, followed by explicit focus
priorities and competing split-lane layouts. Do not infer cause solely from these
owner-observed timings or weaken existing thresholds. Larger resource/fault,
GUI/Neovim, startup, CPU/RSS and Windows/WSL parity gates remain open.

## Reproduce

Use Zig 0.16.0:

```sh
zig build --build-file build-agent.zig agent agent-pty-bench -Doptimize=ReleaseFast
python3 scripts/agent_pty_bench.py --backend all --sessions 8 --load noisy stalled --bulk off mixed --resize-every 16 --runs 3 --samples 1000 --size-mib 10 --output mixed-8.jsonl
zig build --build-file build-agent.zig test-agent-pty -Doptimize=ReleaseSafe
python3 -m unittest discover -s scripts/tests
```

The runner owns a unique local 16 KiB zero fixture. Remote fs experiments require
an explicit prepared `--bulk-path`; no remote deployment/cleanup is inferred.
Mixed mode can use at most 14 shared PTYs because two bulk workers count toward
the existing 16-job cap. A 16-PTY mixed matrix is rejected, not silently downsized
or used to justify raising production limits.
